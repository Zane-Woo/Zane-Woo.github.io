手写spring-day6

前言

这次 coding 很吃力，两天才敲完，当然有我拖延的原因 🤣 但是还得吐槽一句这个 bugstack 的文章写的太 💩 了。他仅仅是把一些核心的改动讲解一下，而且讲解的大多停留在功能逻辑的介绍上，却忽略对于类或接口的设计，而且经常会新增或者修改一些类或者接口的实现，这导致我再把实现的过程中必须时常去翻他的源码对照着敲，不仅费时费力，而且常常让我对这些莫名其妙的修改而困惑。总之，这人的文章质量不是很高。

背景

这次的更新是针对两点

  • 提供可由开发者自定义的对于 Bean 的扩展接口，以便让开发者能够在不同的时机，例如：BeanDefinition 加载后，Bean 属性注入之后或者是 Bean 的 init 方法执行前后去执行一些自定义的逻辑（修改 BeanDefinition/Bean 亦或是执行一些如前置校验的逻辑）。
  • 预实例化：仿照 spring 的做法在传入配置路径的就提前将所有的 Bean 加载到内存中（提前检查错误，加快程序响应）

如果要达成第一点，要解决的问题是：要想在这些 时机 实现自定义逻辑 ，必然需要将这些时机抽象出来并编排成一个标准化的流程（由若干个函数组成），并在这个流程的各个时机插入一些特殊处理的接口。而要达到第二点必须在第一点的基础上，将预实例化加入这个 sop 中，传入配置路径后便可达到目的。直接实现但是问题是原本的 BeanFactory 仅仅负责 BeanDefinition 以及 Bean 的存储以及单个 Bean 的实例化操作，而且之前的 Bean 都是只有在 getBean 后才会去加载，是被动地、懒加载的。为了实现流程的统一编排，我们必须抽象出一个更高层的类/接口来完成这一个工作。也就自然而然地引出了 ApplicationContext

BeanFactory 相关实现

ListableBeanFactory

主要的职责是做一些批量的信息获取操作。注意是关注容器内的存储的 Bean 及其 BeanDefinition 的 统计信息。

AutowireCapableBeanFactory

一个 Bean 创建的具体的过程则是这个接口及其衍生类负责的（如 AbstractAutowireCapableBeanFactory）。

目前主要是针对 Bean 的初始化的前后这一生命周期的阶段进行前置和后置的操作。

但是说实话这个命名确实有点迷，从名字上我只能看出来这个这是一个负责自动装配的 BeanFactory。

HierarchicalBeanFactory

源码中也不多，直接贴出来了，虽然当前还没有实现。

这个接口的意义是赋予容器的一个 层级关系（父子）。具体来说是针对 Factory 的一个层级关系。

不过要注意的是，这个父子关系的建立是通过引用而不是通过创建或者持有实现的，而且这个父子关系是针对每一层的 BeanFactory 而言的而不是针对某一层的所有 Bean。

问题：Bean 容器为什么要进行分层呢？或者说分层是为了解决什么问题呢？

  • 依赖倒置问题： 一个 Bean 可能会依赖另外一个 Bean。但是每个 Bean 的职责和特性不同。所在的分层也不同。正向的依赖关系是指：高层的 Bean 容器会去依赖底层的 Bean 容器（典例 Controller-> Service-> DAO-> String(举例)）。但是反过来就会产生依赖倒置的问题。依赖倒置会引发的问题：模块难以复用（引入 Service 层却需要将 Controller 层引入），关注点模糊（Service 层只应该关注自己的业务逻辑而不需要关注 Controller 层的实现）
    • 高层和底层的判断标准：越接近业务逻辑和用户意图，越具体的 Bean 处于高层，而越具有通用性，越抽象的 Bean 越接近底层。
  • 热启动问题：修改了高层不影响底层的服务运行。

ConfigurableBeanFactory

这个接口的职责是管理 BeanFactory 本身的配置，即与 Bean 相关的元数据 的配置如 Bean 的作用域，BeanPOstProcessor 等。

这个接口可以对照 AutowireBeanFactory 来理解，后者是针对具体的 Bean 创建，前者则是关注所有或某一类的 Bean 的全局配置。

ConfigurableListableBeanFactory

Java 的 接口是支持多继承 的，这很有趣。这个接口继承了上述的所有接口，可以说他是集成所有能力的工厂，所以它可以参与到容器启动的过程中。

Context相关实现

ApplicationContext

这是真正意义上的容器，这里唯一要注意的是它继承了 ListableBeanFactory

ConfigurableApplicationContext

这个接口声明了容器的核心功能：refresh 的方法

AbstractApplicationContext

这个 context 则是负责定义了 refresh 即启动容器的完整逻辑：

  1. 加载 Bean 工厂，并读取配置文件注册所有的 Bean 定义到内存。
  2. 执行加载 BeanDefinition 后的处理操作，即去实例化 BeanFactoryPostProcessor 然后执行它的处理逻辑
  3. 预先实例化 BeanPostProcessor 并放入 factory 的存储的 BeanPostProcessor 列表中。
  4. 预先实例化所有的 Bean。

问题：

  • 为什么要存 BeanPostProcessor？为什么不存 BeanFactoryPostProcessor？
    • BeanFactoryPostProcessor 在 refreshBeanFactory() 之后实例化并且就能立刻发挥作用，但是前者需要在 beanFactory.preInstantiateSingletons() 的过程中发挥作用，所以必然要成为 beanfatory 的一个变量，从命名语义上来说也应该这样。

在这里要把Processor也看作特殊的Bean。

完成refresh的逻辑需要的依赖有：BeanDefinitionReader（读取文件并注册bean），BeanFactory(注册，预实例化)

AbstractRefreshableApplicationContext

负责BeanFactory的创建与管理。注意：不能提前创建工厂，不然违背refresh的逻辑，即工厂的创建时期是由refresh决定的。

创建工厂之后便是解析文件并且加载定义了，这一逻辑交由子类完成。

AbstractXmlApplicationContext

这个主要是负责实现针对xml文件类型的解析逻辑。具体的路径存储与获取则是交给子类实现。

ClassPathXmlApplicationContext

这个主要是负责存储classpath类型路径。

感悟

这个类/接口的设计我感触很多啊。AbstractApplicationContext实现refresh需要factory和reader，但是它不管，只实现业务逻辑把涉及的依赖交给子类实现，AbstractRefreshableApplicationContext只负责创建factory，加载文件交给子类，AbstractXmlApplicationContext只负责用Reader解析文件，保存路径交给子类。

这就是模板模式和分层设计的最好的证明啊！太优雅了！让上层只关注业务逻辑的定义，将一些与底层无关的实现细节交给子类实现。这样不仅能够极大地减少耦合度还能提高扩展性。太牛逼了。
