手写spring-day5

Created2025-12-27|Updated2025-12-30|学习codingjava编码mini-spring
|Word Count:2.4k|Reading Time:9mins|Post Views:

背景

在之前的实现中，容器中的 Bean 对象都是手动注册的，这不仅编码量大而且会将变量属性硬编码到程序中，违背了之前所说的程序和环境分离的实践。在 spring 框架中，是可以通过解析 xml 文件 中的 bean 的定义然后将 xml 中的 Element 的相关属性映射到内存中的 BeanDefinition 对象当中，然后再将该 BeanDefinition 注册到容器里面。这里面最重要的是完成两件事：解析 xml 与 映射成 BeanDefinition 对象。当然，最终目的就是将配置里的 bean 定义自动注册到内存里面，所以我们定义了一个专门处理这个事的接口：BeanDefinitionReader，而被操作对象 xml 文件，我们则抽象出了一个 Resouce，用于定义配置文件。

类与接口的设计

配置相关

Resource

外部的存储文件存储在硬盘，通过 URI 定位，而代码是在内存中运行的，我们如果想解析一个文件，就必然要把该文件加载进内存再进行读取。而无论载入内存的是 Class 还是 File 亦或是 URL，想要去读取他们都必须获得其对应的 InputStream。也就是说，虽然不同类型的文件有不同的路径定义，但是操作他们的方式都是相同的：获取对应的 InputStream 或 OutputStream 对象。所以对于读取的 Resource 的接口来说，只需要定义一个获取输入流的方法即可，具体的路径定义则交给相应的抽象类或者类定义。这是 Java IO 的知识。

可以说之后衍生出的三个不同的 Resouce 类型都是因为 URI 的格式不同，或者说定位方式不同才出现的三个类，但是它们最终都会返回各自的输入流。

ClasspathResource

这是类路径的 Resource。classpath 之前也说过了，他是针对 Java 项目的一种相对路径，所以可以屏蔽不同系统的路径差异。这里是获取对应的 ClassLoader 来调用其对应的 getResourceAsStream 来获取输入流。注意，这并不意味着 ClassLoader 可以加载这个文件，所谓 加载 是指：将字节码文件解析到内存中并可以转换成 JVM 识别的运行时的 Class 结构。 很显然，xml 文件连内存都没进，classLoader 仅仅是提供了一个定位的 API, 加载和解析到内存的的逻辑还得我们操作 InputStream 去完成。

FileSystemResource

针对文件系统的 resource，没什么好说的。

UrlResource

定义访问远程文件的资源 url，有个要注意的点是他要额外获取一个连接对象，根据这个对象获取输入流。这里特判 Http 的原因是只有 http 提供这个关闭连接的接口 😂

文件解析相关

在此之前，先看一下整体的结构，文章中对于接口，抽象类和实现类的职责定义以及规范让我受益匪浅，这是一种很成熟的设计思想

接口：BeanDefinitionReader、抽象类：AbstractBeanDefinitionReader、实现类：XmlBeanDefinitionReader，这三部分内容主要是合理清晰的处理了资源读取后的注册 Bean 容器操作。

接口管定义，抽象类处理非接口功能外的注册 Bean 组件填充，最终实现类即可只关心具体的业务实现

接口只需要关心如何定义一套 行为规范，抽象类负责通用的，公共的 基础资源 的管理，而子类只需要关心如何实现具体的 业务逻辑 即可

这体现了较多的设计思想，下列引用 Gemini 的话：

  • 接口隔离原则 (ISP) 和 面向接口编程。

    • 作用：接口只定义“做什么 (What)”，完全不关心“怎么做 (How)”。它对外暴露的是一套纯粹的功能契约。

  • 单一职责原则 (SRP)。

    • 作用：具体类只需要关注差异化的部分。因为脏活累活（资源管理）被父类干了，规范定义（接口）被接口干了，它只需要实现最核心的“业务逻辑”。

BeanDefinitionReader

BeanDefinitionReader 需要完成 解析文件 和 注册 BeanDefinition 两个行为。这两个行为即：LoadBeanDefinition

  • 解析文件：需要获得相应文件类型的输入流，这个是通过之前的 ResourceLoader 获取的，所以这里需要定义一个 getResourceLoader()

  • 注册 BeanDefinition：因为 DefaultListableBeanFactory 实现了 BeanDefinitionRegistry , 所以注册 Bean 是由 DefaultListableBeanFactory 完成的，但是我们又只需要注册这一个行为即可，所以只去定义了 getRegistry()，传参的时候传 DefaultListableBeanFactory 即可。

涉及到的资源加载器和 bean 注册器也是存给实现该接口的抽象类。

AbstractBeanDefinitionReader

没啥好说，负责基础资源的管理

XmlBeanDefinitionReader

解析 xml 文件有很多方式，如 DOM，SAX，Jackson 等，这里我们使用的是 DOM，他的主要逻辑就是把 xml 转换成树状结构，核心的流程就是获取对象 document，再根据 document 拿到根对象之后获取其子节点，然后再遍历子节点。我上面写的可以当成 DOM 处理的模板了。

附：BeanDefinition 和 Bean 实例我之前以为是分别放在 Beanfactory 和 DefaultSingletonRegistry 里面的，今天看才发现不全对，宏观来看是全都放在 DefaultListableBeanFactory 里面。

因为 DefaultListableBeanFactory 是 AbstractFactory 的子类，而 AbstarctFactory 又是 DefaultSingletonRegistry 的子类，所以 DefaultListableBeanFactory 还有一个父类对象 DefaultSingletonRegistry 的，Bean 实例是存在父类对象 DefaultSingletonRegistry 的 map 里面，但 BeanDefinition 确实是存在 DefaultListableBeanFactory 内部的。不过从宏观来看，这个工厂把定义和实例化对象都存进去了。
