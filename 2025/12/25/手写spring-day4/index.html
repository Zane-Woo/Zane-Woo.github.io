|Word Count:1.6k|Reading Time:5mins|Post Views:

背景

这次的更新主要是针对 Bean 的属性的更新，因为我们之前的 Bean 的定义只有 Bean 的类型信息，对于一个对象的定义而言，这是不合理的，所以要加上属性相关的定义。而对于新增的属性，我们自然而然可以单独抽象出一个类 PropertyValue, 但是一个 Bean 对象肯定不止一个属性，所以 Bean 的属性是 PropertyValue 的集合即 PropertyValues。紧接着，Bean 的创建逻辑就得做出相应的修改。之前我们在创建的时候没有属性注入这一环节，现在我们就需要根据预先定传入的 BeanDefinition 中的 PropertyValues 去进行新创建的 Bean 的属性注入，这个环节体现在 AbstractAutowireCapableBeanFactory 中的 createBean 函数中。这次在 createBeanInstance(beanDefinition, args) 之后添加了 applyBeanPropertyValues(name,bean,beanDefinition)

但是还是有一个问题，就是对于 Bean 的属性来说，必须要考虑一个特殊的情形，那就是一个 Bean 作为属性的类型。这里我们抽象出了一个 BeanReference 单独处理。

类的设计

PropertyValue

这是属性的对象定义。name 指的是属性的名称，主要是靠这个名称去匹配属性并注入值，value 则是属性的值。

为什么没有提供 set 的方法？

在 spring 框架中，bean 的属性并不是在运行时进行配置，也就是说在 JVM 启动之前 bean 的属性就已经定义好了，每次 bean 属性都是通过加载 xml 文件或者.properties 配置得来的。所以 bean 对象属性的修改权在开发人员手中。为什么要将变量值的定义与程序分离呢？我觉得 Gemini 给的解释非常到位：

我们剥夺代码“决定属性值”的权力，是为了把“做什么（逻辑）”和“是什么（数据/配置）”分开。

  • Logic (Code)：应该是稳定的，通用的（无论是开发环境还是生产环境，连接数据库的逻辑是一样的）。

  • Configuration (Data)：是易变的，环境相关的。

把易变的东西抽离出来交给开发/运维人员通过文件控制，这就是“外部化配置”的核心价值

程序本身应该关注逻辑处理，这是普适的，对任何变量都通用的。而想变量这种易变因素应该是属于环境，应该外部化到配置当中。

PropertyValues

可以看到，这里的 PropertyValues 是使用了链表的形式存储 Properties。

为什么不使用哈希表存储呢？

因为源码中的 property 对象不仅只有 name 和 value 两个属性，所以哈希表的键值存储不能完全存储这个类的信息量。

为什么获取属性的时候要转成数组呢？

因为这个 properties 属于私密属性，不能被外部修改，也就是和我上面说的一样，程序本身不具有修改属性的权限，所以返回一个数组对象而不是源对象。

BeanReference

这里的 bean 引用类型只有一个属性值 beanName，相当于一个占位符，在进行属性注入的时候可以根据这个类型和 beanName 加载引用的 bean。

为什么只使用一个占位符引用而不是直接使用 bean 对象呢？

我觉得最主要的是处理循环依赖的场景，虽然本次代码并没有解决。

spring 源码对比

Bean 的加载方式

mini-spring

在我们的代码里面，bean 是采用懒加载的方式，虽然是先去 registerBeanDefinition, 但是并不是说有了 BeanDefinition 就会去加载对应的 Bean，而是在调用 getBean 方法的时候再去调用 getBeanDefinition 和 createBean 的方法。这个时候才真正地实例化 bean。

以下是详细流程图：

    sequenceDiagram
    participant User as 用户 (ApiTest)
    participant ABF as AbstractBeanFactory
    participant DLBF as DefaultListableBeanFactory
    participant AACBF as AbstractAutowireCapableBeanFactory
    participant Strat as InstantiationStrategy
    participant Bean as UserService 实例

    %% 1. 触发获取
    User->> ABF: getBean("userService")
    ABF->> ABF: doGetBean("userService")
    
    %% 2. 检查缓存 (第一次肯定没有)
    ABF->> ABF: getSingleton("userService")
    Note over ABF: 缓存为空
    
    %% 3.以此获取定义
    ABF->> DLBF: getBeanDefinition("userService")
    DLBF-->> ABF: 返回 BeanDefinition
    
    %% 4. 开始创建
    ABF->> AACBF: createBean("userService", bd, args)
    
    %% 5. 实例化 (只是 new 出来，属性还是空的)
    AACBF->> AACBF: createBeanInstance()
    AACBF->> Strat: instantiate(bd, "userService", ctor)
    Strat-->> AACBF: 返回原始对象 (userServiceImpl)
    
    %% 6. 属性填充 (关键步骤)
    AACBF->> AACBF: applyPropertyValues("userService", bean, bd)
    
    loop 遍历属性列表
        opt 如果属性值是 BeanReference ("userDao")
            AACBF->> ABF: 递归调用 getBean("userDao")
            Note right of ABF: 这里会重复上述流程<br/>创建并返回 UserDao
            ABF-->> AACBF: 返回 userDao 实例
        end
        AACBF->> Bean: 反射调用 setUserDao(userDao)
    end
    
    %% 7. 放入缓存并返回
    AACBF->> ABF: (逻辑上) 添加到单例缓存
    AACBF-->> User: 返回完整的 userService

这里会出现一个问题：

属性注入在实例化之后，会覆盖掉运行时 getBean 传入的属性值，这合理吗

这合理，因为 配置优先，并且在 spring 中，bean 的生命周期 里的实例化是在初始化/属性填充之前

spring

但是在 spring 中，bean 是在启动的时候就已经预加载了，是饿汉式。

这主要是出于以下几点原因考量

  • 提前加载 bean 能及时发现错误，即 Fail-fast（快速失败）原则

  • 运行时的性能会更高

Properties

在现有的实现中，property 都是手动地注入 beanDefinition 的，但是 spring 是通过扫描 xml 或.properties 文件完成的。但是相对于源码，我们这里少了一个配置文件解析的对象，所以没法完成配置文件的解析。
