HashMap源码学习

Created2026-01-11|Updated2026-01-21|学习codingjava集合HashMap
|Word Count:3.6k|Reading Time:14mins|Post Views:

数据结构

首先是从宏观上去认识。1.7 之前，使用的是数组和链表。为什么是数组和链表呢？因为在存储数据的时候，由于数据量可非常庞大的，但是哈希表的终究容量有限，所以难免会发生不同的数据但是计算出的哈希索引相同的情况这就是哈希冲突。解决哈希冲突的方法有很多种，典型的有 再哈希法，开放寻址法与拉链 法。这里则使用了拉链法（将冲突的数据用链表组织）。

那为什么在 JDK1.8 及之后就使用了红黑树了呢？这里主要是考虑当同一个哈希桶的对应的链表组织的数据多了之后，操作的效率就会下降

(O(n))。所以就会在一定时机将其转换成了树形结构–红黑树 进行存储。

  • 既然红黑树时间复杂度这么低，那为什么每个哈希桶的存储结构不一律使用红黑树却使用链表呢？

    • 我们来看一下官方对于使用红黑树的意见：

    • 可见，一个树节点的内存占用是一个链表节点的两倍之多，并且红黑树的维护成本也高于链表（这体现在虽然红黑树的遍历的次数少，但是每次遍历所做的操作次数是多于链表的），因此红黑树与其说是优化，不如说是一种 内存和时间之间的平衡。在官方的表述中，这更像是一种”兜底“。他说，在理想的哈希函数的随机分配下，节点在哈希表中的分布遵从 泊松分布。可以看到，一个桶中有八个节点的情形概率仅仅只有 0.00000006。所以我们大可以从另一种角度去看待红黑树这一数据存储策略，在一定的数据量下，它更多的是对一个哈希函数好坏的体现，不均匀的哈希函数才会让桶中更高频率地出现红黑树。

    • 另外，抛弃实际的数据分布而仅仅通过时间复杂度去判断一个数据结构或算法的快慢是错误地做法。时间复杂度仅仅是描述一个算法的主要 增长趋势，他往往会忽略常数或更小的级数，并不是对计算效率的精确表述，只能作为估计的大致参照而不是依据。

数据存储

Node

当落实到具体的节点时，哈希表使用了 Node 去进行包装一个 <K,V> 键值对

提一下这里的 hashCode() 的求法，是将 key 和 value 进行不异或操作，因为相等的 Node 对应的 hashcode 必然是相等的（整合两部分信息）

不同的 Map 实现的底层数据结构各不相同，为了实现抽象和实现分离（封装），必须要有一个统一的操作 Map 对象的视图提供通用的操作来屏蔽底层的数据结构的实现细节，所以定义了 EntrySet <K,V>。

从代码实现上可以看出这个视图对于集合数据的操作都是 直接操作 Node [] 数组。

不过自己实现了迭代的操作。

关键属性

threshold 与 loadFactor

threshold 是哈希表的扩容阈值，当哈希表存储的节点数量超过该值时就会触发扩容。对于长度为 length 的 Node [], threshold=length*loadFactor, 这里的 loadFactor（负载因子）就是影响这个扩容的阈值大小，默认是 0.75。负载因子决定动态扩容的触发时机，0.75 是经验值，最好别改。

size

size 是哈希表的实际存储的元素数量，注意和 table 的 length 区分。

modCount

用于记录结构修改的次数（覆盖不算）。主要是用于解决遍历过程中的结构变更的问题。如果在遍历的过程中修改内存中存储的数据结构，就会抛出 ConcurrentModificationException 异常，终止程序。

具体的逻辑是：在获取迭代器 Iterator 的时候，迭代器内部会有一个 expectedModCount, 开始时，会执行

之后每次去执行 hasNext() 方法的时候会比较当前 modCout 与 expectedModCount，若两者不相等，就会抛 CME 异常。

这就是迭代器的 fast-fail 机制。

可能会有问题：

  • modCount 为什么不是线程安全的？万一在多线程的环境下出现计数错误呢？
    • 首先，hashMap 本身就不应该在多线程的环境下使用，这种用法本身就有问题
    • 其次，就算计数出错也不影响迭代器的 fast-fail 机制。因为此机制不依赖修改的具体值

如何理解负载因子与阈值

哈希表的本质就是为了加速元素的查询效率，理想的哈希表能够为每个节点都分配独立的存储空间。但是在实际工程中是永远都很难去避免哈希冲突的发生。

哈希冲突的发生概率大小，取决于哈希算法（使得元素尽可能地均匀分布）的优劣和哈希表的长度。

其实两者是相辅相成的，一定长度的情况下，哈希算法的优劣可以影响冲突的发生。但是足够大的哈希表，差一点的哈希算法也能实现均匀分布；而足够小的哈希表，再好的哈希算法也避免不了冲突的发生。所以有良好的哈希算法的前提下，你的容量不能太小，也不能过大。既不能无限制地浪费内存，也要维持较低的冲突率。

这就引入了 动态扩容机制与负载因子 的设计，根据元素数量动态调整容量，以维持系统的高效平衡。

重要方法

哈希函数和索引计算

在了解这个两个函数之前需要去先明白 hashMap 的扩容的相关属性，哈希表的初始长度是 16，每次扩容也是 2 倍。由于计算索引的时候是对长度取模，所以实际上长度是素数的话会有效减少哈希冲突，但是为什么 HashMap 没有这样去做呢？

  • 核心原因是这样更“快”
    • 长度为 2 次幂的情况下，对二次幂直接取模等价于和（length-1）进行 与操作，而 与操作 会更快（因为取模会涉及除法）
    • 扩容时节点只需要去判断 hashCode 最高位是否为 1 即可（因为扩容后的（length-1）相当于最高位新增了一位 “1”），迁移时更快。

由于 key 的哈希值包含的信息位数更多，所以每次的 与操作 相当于哈希值的低位参与运算，并没有包含高位的信息，为了避免某些极端情况（低位全是0）。所以这里是让高16位和低16位进行了与操作，将高位和低位信息全都包含进去，更为合理。

扩容

最重要的是后面的数据迁移的部分，这里是创建了两个链表用于存储原位置（不需要迁移）和新位置（迁移）

迁移也不需要重新计算哈希，只需要利用 e.hash & oldCap 这个简单的位运算，直接判断是 0 还是 1。

  • 如果是 0：在新数组的位置 = 原位置。

  • 如果是 1：在新数组的位置 = 原位置 + 老容量。
