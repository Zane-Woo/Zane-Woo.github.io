背景

在之前的实现中，我们默认 Bean 是单例模式，并且没有把 scope 当成 Bean 的元数据处理，这次我进行了修正并扩展一个 scope 即 prototype

(原型模式)。

这次新引入的 FactoryBean 是一种特殊的 Bean，它不作为业务 Bean 暴露给用户，它作为 生产 Bean 的过渡第三方，执行用户自定义的 getObject 逻辑获取自定义的 Bean。不过对于这个新概念的引入我一直没有搞明白它到底是为了解决什么问题。之后细说。

类/接口的设计

UML 关系图

BeanDefinition

这是新增的 scope 相关的属性，后续的 get/set 方法就不赘述了。这里主要是只有两种模式，**SCOPE_SINGLETON** 单例模式与 SCOPE_PROTOTYPE（原型模式）

注意：

  • 切不可想当然地把 prototype 当成 多例模式

    • 首先明确一下这个模式下的 Bean 的行为模式：每次在获取 Bean 的时候都会重新创建一个新对象而不是存到内存中之后从内存中获取，并且容器不负责该模式 Bean 的销毁工作。我们不妨再看一下 Spring 对 prototype 的定义：容器在每次请求时创建一个新实例，并仅负责创建，不负责销毁

      容器在每次请求时创建一个新实例，并仅负责创建，不负责销毁

      我觉得这不能称之为 原型模式，wiki 中对原型模式的特性的解释如下：

      其特点在于通过“复制”一个已经存在的 实例 来返回新的实例, 而不是新建实例。被复制的实例就是我们所称的“原型”，这个原型是可定制的。

      我问了 Gemini，spring 源码也是这种设计，直接创建新对象，但这种设计根本不是原型模式甚至跟原型模式背道而驰。但是 Gemini 说 spring 对此也没有一个很好的解释。我很惊讶这个比较重要的设计点却能出现命名误导的错误，真是草台班子嘛？

后续的设计的逻辑修改主要是 XmlBeanDefinitionReader、AutowireCapableBeanFactory

会额外对 xml 中的 scope 属性进行处理，并且在创建 Bean 的时候会检测 scope，如果是 prototype 的类型

就不会存入内存中，也不会对其做后续的销毁处理。

FactoryBean 相关实现

FactoryBean

FactoryBeanRegistrySupport

这个类是负责管理 FactoryBean 的工厂类，两者的关系就像普通的 Bean 和 DefaultSingletonBeanRegistry 一样。

这里的 getObjectFromFactoryBean 进行了作用域判断。doGetObjectFromFactoryBean 才会真正执行 getObject 也就是 FactoryBean 的核心方法。

下面来探讨我对于 FactoryBean 的核心问题。

为什么要有 FactoryBean？

我们知道 FactoryBean 也是 spring 对 Bean 的一个扩展，你可以把 FactoryBean 当成业务 Bean 的工厂代理，用户要的不是前者而是后者，但是 spring 对用户暴露的却是 FactoryBean 而不是真正的业务 Bean。而 FactoryBean 主要负责真正的业务 Bean 的生命周期。

到这里肯定会产生一个疑问:

  • 这听起来似乎 BPP 和 BFPP 就能完成他的所有职能啊？

    • 没错，这个观点是正确的，只不过我们要注意一个细微的差别：BFPP 和 BPP 他们虽然可以对 Bean 的创建过程做逻辑增强，但是没法干预 Bean 的实例化，因为三个处理的时机是分开的，但是 FactoryBean 却是包揽了这个 Bean 从实例化到初始化的全流程，换句话说它接管了一个 Bean 的创建流程。但是这个不代表 FactoryBean 的生态位就是独特的，因为 BPP 完全可以返回一个代理对象来取代 FactoryBean 的职能。

    • 以上的想法在技术上是完全可行的，但在职责边界和语义上却是不合理的：

      1. BFPP 和 BPP 的设计定位：

      • 它们是 Bean 生命周期中的 “修饰者/增强者”，作用对象是已有的 BeanDefinition（BFPP）或已实例化的 Bean（BPP）。

      • 它们不应该接管或替代 Bean 的实例化过程——虽然技术上可以返回一个全新对象，但这属于 “越权操作”，会导致生命周期混乱（比如跳过属性填充、破坏循环依赖处理等）。

      1. FactoryBean 的设计定位：

      • 它是 Bean “创建方式的替代者”，直接接管了对象的实例化过程。

      • 容器不会通过反射调用构造函数，而是调用 factory.getObject() 来获取对象。

      • 这是 Spring 为 “复杂对象创建” 预留的标准扩展入口，语义清晰且符合职责分离原则。

      1. FactoryBean 产出的对象与普通 Bean 的区别：

      • ❌ 没有对应的 BeanDefinition（容器里注册的是 FactoryBean 本身的定义）。

      • ❌ 不会经过完整的 Spring 生命周期管理（不走属性填充、Aware 回调、init-method）。

      • ✅ 但仍会经过 BeanPostProcessor 处理（主要是为了支持 AOP）。

      • ✅ 单例对象会被容器缓存（在 FactoryBean 的专用缓存 factoryBeanObjectCache 中）。

不过FactoryBean有个很独特的应用场景就是可以完成接口的“实例化”。举一个在Mybatis中的很典型的应用。就是用户只提供了一个接口UserDao，但是mybatis仍然可以将它作为依赖注入到其他对象中。具体的流程我就不赘述了，直接贴一个Claude给的：

1. 用户提供的内容

  • 业务接口：interface UserDao { User getUser(Integer id); }
  • SQL 配置（XML 或注解）：

2. 启动阶段：扫描与注册

  • 扫描：MyBatis 扫描器（ClassPathMapperScanner）发现 UserDao 接口。
  • 构建映射表：解析 XML/注解，将 SQL 逻辑封装为 MappedStatement 对象，存入内存 Map：
    • Key: "com.example.UserDao.getUser"
    • Value: MappedStatement（含 SQL、参数类型、结果类型）
  • 注册 BeanDefinition：向 Spring 容器注册 Bean 定义，关键信息如下：
    • beanName: "userDao"
    • beanClass: MapperFactoryBean（这是 MyBatis 提供的通用工厂类，而非接口本身）
    • property: mapperInterface = UserDao.class

3. 实例化阶段：创建 FactoryBean

  • Spring 根据 BeanDefinition 实例化 MapperFactoryBean。
  • 属性填充：将 UserDao.class 注入到工厂的 mapperInterface 属性中，此时工厂已准备好生产代理对象。

4. 获取 Bean 阶段：产生代理对象

  • 触发创建：当业务代码请求 getBean("userDao") 或 @Autowired 注入时。
  • 识别工厂：Spring 发现该 Bean 实现了 FactoryBean 接口，转而调用 factory.getObject()。
  • 动态代理：getObject() 内部使用 JDK 动态代理生成对象：
  • 注入：Spring 将生成的代理对象（$Proxy0）注入给业务 Bean，而非工厂本身。

5. 运行时：拦截方法调用

  • 调用：用户执行 userDao.getUser(1)。
  • 拦截：调用被转发到 MapperProxy.invoke(proxy, method, args)。
  • 查表与执行：
    1. 拼接 Key："com.example.UserDao.getUser"。
    2. 查映射表：找到对应的 MappedStatement（获取 SQL）。
    3. 执行：参数绑定 -> JDBC 执行 -> 结果映射。
  • 返回：将数据库结果转换为 User 对象返回给调用者。

这里最大的疑惑是没有函数定义是怎么执行函数的，因为jdk最后invoke的时候还是得调用声明的函数，后来知道没有mybatis是通过建立一个函数名和sql语句的映射，所以实际上这个接口的方法从来没有被实现过，真正调用的时候只会用到函数名，然后从map里面找就可以了。
这个好处很多，减少了编码工作，无需实现类。而且易变的sql语句放在配置文件里很符合环境与程序分离的编码实践。

这FactoryBean困扰我一下午，一直没法弄明白为什么要有这个概念，后来跟gpt唇枪舌剑之下才稍微弄清楚门道。
