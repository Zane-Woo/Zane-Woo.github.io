背景

如何理解 spring 和 AOP 结合呢？

核心逻辑

AOP 的核心目标是对 具体的方法 进行增强，但在 Spring IoC 容器中，这种增强是通过 代理对象（Proxy） 来实现的。

只要一个 Bean 中有任何方法需要被增强，容器就需要用一个包含了增强逻辑的 代理对象 来替换原始对象。因此，AOP 与框架结合的关键点在于：如何介入 Bean 的生命周期，在 Bean 创建完成后，自动判断并返回代理对象。

实现方案

这一扩展逻辑最适合通过 **BeanPostProcessor**（Bean 后置处理器）来实现。

具体流程如下：

  1. 介入时机：利用 BeanPostProcessor 的 postProcessAfterInitialization 扩展点，这次实现中是在实例化之前去进行代理对象的处理。其实这并不完善。
  2. 自动匹配：遍历容器中所有的切面（Advisor），根据切面的切点和当前 Bean 判断当前 advisor 是否符合条件。
  3. 创建代理：如果匹配，则利用动态代理技术（JDK 或 CGLIB）生成包含对应增强逻辑（Advice）的代理对象。
  4. 替换返回：将生成的代理对象返回给容器，替换掉原始的 Bean 实例。

在本次实现中，这一核心逻辑由自定义的 BeanPostProcessor 实现类 —— DefaultAdvisorAutoProxyCreator 来完成。

上面回答了如何处理生成代理对象的问题，之后问题是：

如何将第三方的增强逻辑（之后称之为 Advice）以及过滤条件注入到容器中并融合进生成的 proxy 对象里面呢？

在回答这个问题之前，我们得先明确上个版本的 AOP 实现存在的问题。

在上一个版本的实现中，我们理解的增强逻辑对应的是 MethodInterceptor，我们把这 Interceptor 和 Pointcut 都放入了 AdviceSupport 中，而每一个代理对象都持有一个 AdviceSupport 这一核心属性，也就通过该属性使得代理对象在执行方法的时候，能过滤需要执行增强逻辑的方法对象，并调用对应的 Interceptor。

  • 问题一：原先的实现中，MethodInterceptor 并不是纯粹的 Advice 对象，因为它不仅仅负责增强逻辑的实现还需要关注原方法的调用时机。这违反了职责分离的原则，代码耦合度高。
    • 所以解决方法是抽象出负责增强逻辑的类即 Advice, 它只负责增强逻辑的编码工作，不负责原方法的调用时机。而 MethodInterceptor 则是负责执行增强逻辑和调用原方法。这样还有个好处就是，可以将增强逻辑进一步根据调用时机进行细分。这样就可以提供给用户拥有更为友好的扩展性。
  • 问题二：原有的实现中，Poincut 和 Advice 是分离的
    • 实际上，在定义一个 Advcie 的时候，就必然要去指定这个增强逻辑的生效的目标对象或方法，也就是说增强逻辑必然要指定匹配逻辑。Advcie 与 Pointcut 是 N 对 N 的关系，所以我们就使用 Advisor 对象去进行包装。
  • 问题三：原有的实现中，一个 AdvisedSupport 对象只对应一个 Advisor
    • 一个对象可能会有多种增强的逻辑（如日志，参数检查等），所以这是不合理的，所以我们新增了 Advisor 的集合并使用 List 存储。具体的实现之后介绍。

类/接口的设计

相关类/接口关系图

先介绍对原先实现的改造工作

AdvisedSupport

  • 新增 Advisor 类型的集合。

  • 新增根据方法返回所有的拦截器对象。

  • 新增用于判断需要何种代理对象的字段（毕竟是一个 proxy 的核心字段）

getInterceptors() 方法是根据一个 method 对象返回所有匹配的 advisor 的所有拦截器。

原先我认为一个 method 对象不能唯一确定一个方法，事实上我错了，因为 method 对象里面就已经包含了类名，参数类型数组所有必要的信息，所以完全可以确定。

proxyTargetClass 字段主要是为了配合 Proxyfactory 来决定去返回什么类型的代理对象。

  • 注意：所有的诸如Advcie、pointcut等涉及

ReflectiveMethodInvocation

在上一个实现中，这个 ReflectiveMethodInvocation 主要是被当成包装原方法的一个包装类。主要的作用是提供给拦截器调用原方法的接口。但是这次的实现中它不仅负责原方法的调用，它也会去协调这个方法匹配的所有的拦截器的调用，具体是通过 责任链模式 来实现(本质上是通过递归)。

主要是修改了 proceed()的实现，并且新增了所有匹配到 method 的拦截器对象这一属性。

currentInterceptorIndex 作为计数器记录当前执行到了哪一个拦截器。当所有拦截器执行完之后才回去执行原方法。

注意这里封装了原方法的执行逻辑，主要是为了应对如 Cglib 的代理对象需要使用 methodProxy 才可以执行原方法的逻辑。

随着ReflectiveMethodInvocation的修改，代理类的对应的invoke的逻辑也需要进行修改，下面以jdk为例

现在的逻辑变成：先获取method对应的所有拦截器，在包装成ReflectiveMethodInvocation后去直接执行这个对象的proceed方法。

ProxyFactory

主要是通过 AdvisedSipport 来判断返回何种类型的代理对象。

默认是 Cglib 类型。

后续才发现 Jdk 代理有太多弊端。只能代理目标类的接口，并且返回的代理对象只能转成接口不能转成目标类（兄弟类）。

DefaultAdvisorAutoProxyCreator

本次实现AOP融入spring的核心类，是处理 Bean 并能返回代理对象的 BPP。

注意这里的方法名称为postProcessBeforeInstantiation，是指在实例化之前调用的方法（不是初始化）。主要逻辑是找出匹配当前Bean的所有Advisor对象，并封装成AdvisedSupoort以创建代理对象。

也就是说，所有的advisor对象（无论是pointcut还是advice）都是提前作为bean注册好了，我们要做的仅仅是在Bean实例化的时候去利用切点判断这个Bean需不需要代理就可以了。

下面就是介绍融入spring的具体实现

CreateBean

在实例化之前会进行一个前置处理。如果不需要代理那么resolveBeforeInstantiation就会返回null，之后就会走正常的创建流程。

applyBeanPostProcessorBeforeInstantiation会真正执行代理对象加工方法postProcessBeforeInstantiation。

很有意思的是，这里会在代理对象加工出来之后调用applyBeanPostProcessorsAfterInitialization，主要的疑问就是：

  • 为什么没有去调用这个方法对应的Before，仅仅调用了一个After，这合适吗？

    • 下面贴个Gemini的回答，我觉得挺有道理的

      • postProcessBeforeInitialization 是设计用来在 “init-method 执行之前” 运行的。既然你拦截了实例化，导致连对象都是替身，原来的初始化流程根本不存在了，所以自然就不需要执行 BeforeInitialization 了

    • 的确，你这个返回后的代理对象根本不是源对象，所以不需要进行源对象的实例化操作，但是还是得保留一个给其他的BPP处理的机会。

不相关的问题

也是在写这个AOP的时候发现的，原先的容器启动时的预实例化本质是调用newInstance，但问题是这个newInstance方法本质上就是调用这个类的无参构造函数，可是如果一个类没有无参构造函数该怎么办？

对了，在当前的postProcessBeforeInstantiation实现中，也是调用无参构造函数进行实例化Bean的。

这是一个坑。之后看看源码怎么做的，看完之后再修正一下
