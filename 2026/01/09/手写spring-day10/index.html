背景

在实际场景中，一个业务的操作往往是由多个逻辑操作完成的。比如购买商品需要提交订单，支付，落库，返回支付结果等多个操作。但是为了保证这些功能是解耦的，所以必须要能让不同的业务操作能够感知到其他业务操作的状态，而容器事件监听可以很好解决这个问题。

但是还是有一个问题，那就是这和消息队列有什么区别？能不能只用这个或者只使用消息队列？两者在真实业务场景上有什么硬性的差别？

类与接口设计

完成事件的监听需要三个部分的参与，一个是消息生产者，一个是消息的中转者，一个是消息的处理者。在本次实现中，分别你对应 publisher，multicaster 与 listener。当然，消息本身也是需要进行定义的，这里对应的是 Event。下面看具体的实现。

类/接口的关系框架图

这里的结构分为三个部分：事件，广播器与发布者。因为这里的监听的事件都是容器的事件，所以这里的发布者仅仅是针对容器及其内部对象。

Event 类

对于 Event, 只需要关注最上层的 EventObj 即可，其他的业务事件的相关属性取决于具体的业务。这里的业务事件只介绍 ApplicationContextEvent。

EventObj

这里的核心的关注点就只有一个，那就是 source，即 事件源。

  • 注意：这个 EventObj 只提供了有参构造函数，这意味着 子类在初始化的时候必须要提供事件源。

不过还有一个值得关注的，那就是 transient。

来看一下 Oracle 官方对于 transient 的 解释：

In the Java programming language, transient is a keyword used as a field modifier. When a field is declared transient, it would not be serialized even if the class to which it belongs is serialized. In Java, methods, classes and interfaces cannot be declared as transient, because they are never serialized

摘自 Wiki

从 transient 的定义可以得知，transient 的使用场景是 序列化。具体来说就是 出于安全或者性能的原因，比如说待序列化的对象的某字段是敏感的或者过大，所以会使用 transient 关键字来标记该字段，效果就是在序列化的时候就会自动忽略这个字段。

但是这同样会有个问题：

  • 忽略这个字段导致对象的必要信息丢失怎么办？
    • 解决方法可以是提取这个字段的必要的部分信息作为属性而不是将全部的信息作为属性。

还有个要注意的是，Java 中实现对象的可序列化，必须让对象实现 java.io.Serializable 接口

ApplicationContextEvent

这个专门代指容器的相关事件，后面的 ContextClosedEvent 与 ContextRefreshedEvent 就是代表具体的业务场景。

ApplicationEvent 则是代表所有和 spring 相关的事件。

广播器类

最上层的广播器接口只是声明了增减监听者以及广播的方法。这表示广播器 不仅执行具体的广播行为，也承担对监听对象的存储工作。

值得关注的是，这里的 multicastEvent() 并没有提供具体的算法实现，而是可以通过多态来实现所谓的 策略模式

这么看，策略模式其实也没有什么东西，我的理解仅仅是通过接口声明一个统一方法，再由多态动态执行实际逻辑而已。

其实这里最主要去关注的是 AbstractApplicationEventMulticaster 的相关逻辑实现。当然，我们这里的实现的广播事件的处理逻辑是 同步 的.

那么问题来了，我们在执行这个判断逻辑的时候，参数给的是 ApplicationListener 类型，问题是如何得到这个泛型的实际参数呢？

注意，这里的 ApplicationListener 仅仅是一个引用，但是他指向的是原来的实例对象，我们可以通过 getClass()获取实际的类对象。

  • 由于泛型的 类型擦除机制，泛型的参数在运行时都会 被替换为 Object 或类型边界。但是实际参数仍然会保留在 类的元数据 里面。所以我们仍然可以通过 getGenericInterfaces() 方法获取 未被类型擦除的接口对象。

另外，这里的接口是使用 Type 类型（是 Class 的父类）。

  • 为什么要有这个类型呢？只是用 Type 不行吗？

    • 泛型出现之后就无法满足需求了。举个例子，List 类型和 List<Integer> 的区别是后者有泛型参数，实际上两者的元数据不一样，后者比前者多了一个泛型参数，Java 的解决方法是在 Class 的基础上再抽象出一个 Type，这个 Type 可以表示 Class 与含泛型参数的接口。

    • 那么问题来了：为什么不去在 Class 类型中加一个对应的泛型参数的字段呢？

      • 主要的原因是为了兼容之前的代码，泛型是之后才加入的 ，之前的不同泛型参数的对象的 instanceof 比较类型的时候都是相同的，如果加了一个字段必然是矛盾的，所以这就是为了擦屁股妥协的结果。

    • 有泛型参数的 Type 是 ParameterizedType(这是 Type 的一个子类，表示有参数的)。

      • getActualTypeArguments 就是获取该泛型的实际类型参数

      • rawType 就是泛型本身的类型，比如 ApplicationListener ，它的 RawType 就是 ApplicationListener.class。

      • getOwnerType 只有在处理内部类的时候才会使用到。

    • 还有一个要注意的是在进行 instanof 比较的时候，比较的是 rawtype

    • 泛型为了实现在类型擦除之后仍然能正常调用原方法（因为擦除之后类型都变了），会使用 桥接方法机制

扯多了，但是这下就明朗了，我们这个 ApplicationListener 是指向原实例的指针，所以通过 getClass 获取原实例，再通过 getGenericInterfaces 获取所有未被类型从擦除的接口，拿到 ApplicationListener 类型的 Type，再去拿到这个接口的泛型参数，也就是监听的 Event 的类型，再去看看这个 Event 是不是给定的 Event 类型的父类即可。
